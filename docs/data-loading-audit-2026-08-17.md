# Data-Loading Audit — 2026-08-17

## Scope and method

This audit examined **user-visible data delivery**, rather than merely whether a request returned a successful HTTP status. It covered the MLB Stats API proxy, Baseball Savant proxy, FanGraphs models, financial and contract sources, provider identity resolution, news, intelligence calculations, and the desktop/mobile interfaces that present those results. Each probe classified a response as **loaded**, **unavailable**, **provider-blocked**, or **HTTP error**; it also recorded cache behavior, response shape, row counts where applicable, and browser request failures.

The audit was performed against the local SKIP application on 2026-08-17. The saved machine-readable endpoint and UI results are generated by `scripts/live-data-audit.mjs`, `scripts/ui-data-audit.mjs`, and `scripts/player-profile-load-audit.mjs`.

## Interface coverage

The browser audit traversed Overview, Players, Prospects, Draft, League, Intelligence, Intel Feed, and a player profile at both 1440 × 1000 desktop and 390 × 844 mobile viewports. All 16 workspace/view combinations rendered without an error boundary or recorded browser request failure. Pages with a currently unavailable source exposed a visible loading, coverage-gap, or unavailable state.

The visual review confirmed that the desktop Overview keeps verified team data visible while isolating FanGraphs-dependent values inside explicit unavailable/coverage-gap states. The mobile profile maintains a readable layout with the profile card, MLB statistics, and confidence strip available without requiring optional historical enrichment to finish first.

## Verified repair: non-blocking player profile delivery

The audit found a real usability defect: `loadFullPlayer` awaited the recent official-boxscore aggregation before committing the profile. That optional aggregation can require a large game window and left the mobile profile in a full-page skeleton long after core profile, season-stat, and Statcast requests were ready.

The repair now creates an explicit `loading` boxscore state when a player has a current MLB team, renders the profile immediately after its core data resolves, and hydrates official boxscore splits in a background effect. If the background request fails, the boxscore panel transitions to an explicit unavailable state with a retry instruction; it never leaves the profile perpetually loading. The retry path now obtains the correct team ID from `player.profile.currentTeam.id`.

A post-repair mobile verification loaded a usable Shohei Ohtani profile in **2,539 ms**, with the data-confidence strip and performance summary visible, no profile skeleton, and no browser request failures. The repair preserves the dedicated panel’s visible loading state while official boxscore rows continue to hydrate.

## Operational guidance

The audit scripts are intentionally repeatable. Run the following after a provider, cache, or UI change:

```bash
node scripts/live-data-audit.mjs
node scripts/ui-data-audit.mjs
node scripts/player-profile-load-audit.mjs
```

The external source limitations observed here are operational, not data-integrity failures. They should be monitored as provider availability changes, while the application continues to display explicit provenance and unavailable states rather than substituting estimates for missing verified data.
