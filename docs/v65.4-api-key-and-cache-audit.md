# v65.4 API-Key and Cache Audit

## Scope

This note records a passive comparison of `SKIP_baseball_v65.4_debugged_optimized.zip` against the current managed SKIP project. Archive contents were listed and read as text only; no archive code was executed.

## API-key findings

The v65.4 archive does not contain an `.env` file, credential file, API-key value, bearer token, or provider-specific secret. Its MLB, Savant, NCAA, feed, and contract modules call public upstream URLs through Vercel-style serverless proxy routes. The archive’s `package.json`, `vercel.json`, README, and source files do not define a required MLB, Savant, FanGraphs, or Spotrac API key.

The current project follows the same public-upstream model. Managed environment variables are used for application infrastructure, authentication, database access, analytics, and the explicitly gated staging failure hook; no external baseball-provider secret was found in the source comparison. No key or token from the archive was copied.

## Cache and request findings

The strongest request-minimization pattern in v65.4 is a small client cache plus an in-flight promise map around the shared MLB fetcher. It uses a 20-second default client freshness window, a five-minute leaderboard window, and removes failed promises from the in-flight map. The archive’s server MLB proxy mainly supplies CDN `s-maxage` and stale-while-revalidate headers rather than a warm-instance response cache. Its Savant proxy advertises a one-hour CDN cache despite comments saying the data changes daily.

The current project already had the stronger server-side Savant policy: successful Savant responses expire at the next UTC midnight, stale snapshots remain available during provider failures, and concurrent requests coalesce. It also had a more defensive MLB client queue, stale reuse, provider cooldowns, and server warm-instance caching.

## Verified changes applied from this comparison

The current team-financials server handler had two rate-limit decisions on the same request path. One occurred before the fresh-cache and in-flight checks, which meant repeated cache reads could consume rate-limit budget even though they did not contact Spotrac. The duplicate decision was removed; the single rate-limit check remains immediately before a new upstream fetch.

The browser team-financials cache previously retained a successful promise indefinitely. It now reuses the result for 30 minutes, matching the server freshness window, then permits a legitimate refresh. Failed results still evict immediately so a later attempt can recover.

Contract data now has browser-side in-flight coalescing and a six-hour freshness window aligned with the contract proxy’s six-hour CDN policy. Failed contract requests are evicted rather than permanently cached, so a transient provider failure can recover.

Regression tests now cover team-financials warm-cache reads beyond the rate-limit threshold, server in-flight coalescing and stale fallback, 30-minute browser freshness, contract concurrent reuse, six-hour contract refresh, and contract failure recovery.

## Conclusion

The archive did not reveal a hidden API key or a missing credential that explains the current request problem. Its useful reliability pattern was request identity plus short-lived client caching and in-flight deduplication. The current project already implemented that pattern for MLB and extended it to server-side provider caches; this pass additionally removed a real duplicate rate-limit check and bounded two browser caches so requests are minimized without freezing data forever.
